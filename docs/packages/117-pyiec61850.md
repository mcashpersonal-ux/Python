# 99 — IEC 61850 with pyiec61850

> `pyiec61850` provides Python bindings for [libiec61850](https://github.com/mz-automation/libiec61850), allowing an automation or protection application to browse IEC 61850 logical nodes, read and write data attributes, and work with reports and control blocks. Start with reference and data-quality handling offline; connect to an IED only after the model and test network are verified.

## Install

```bash
python -m pip install pyiec61850
```

The package is a compiled binding rather than a pure-Python library. Its PyPI releases are versioned pre-releases (for example, `1.5.2a1`) and wheels are platform/Python-version specific; a wheel may not exist for your interpreter, operating system, or CPU. If installation cannot find a compatible wheel, use a supported CPython version or build the libiec61850 binding according to the project instructions. Pin the version used in a protection-system test, and do not silently replace it with an unrelated IEC 61850 implementation.

## Start offline: validate an IEC 61850 object reference

This first example is deliberately **local and demo-safe**. It does not import the native extension, open a socket, or require a display or an IED. It checks the dot-separated reference shape that an adapter might receive from a station configuration before passing the reference to `pyiec61850`.

```python
import re

reference = "Bay01/LLN0$ST$Mod"
match = re.fullmatch(r"(?P<logical_device>[^/]+)/(?P<logical_node>[^$]+)\$(?P<fc>[^$]+)\$(?P<data>[^$]+)", reference)
if match is None:
    raise ValueError(f"Invalid IEC 61850 reference: {reference}")

parts = match.groupdict()
allowed_fc = {"ST", "MX", "CO", "SP", "SV", "CF", "DC", "EX"}
if parts["fc"] not in allowed_fc:
    raise ValueError(f"Unexpected functional constraint: {parts['fc']}")

print(parts)
```

IEC 61850 references vary by server model and application. Treat this as an input-validation pattern, not a universal parser: obtain the authoritative logical-device, logical-node, data-object, and functional-constraint names from the IED's SCL files or a controlled discovery step.

## Connect to an IED and read a value

`pyiec61850` exposes the libiec61850 client operations through the `iec61850` module. The following is a **live-device example**: it assumes an IED or test server is reachable at `IED_HOST` on MMS/TCP port `102`, and the reference exists in that server's model. It performs no connection when copied into the offline example above, so keep this section out of production until the endpoint is approved.

```python
import os
import pyiec61850
from pyiec61850 import iec61850

host = os.environ.get("IED_HOST", "192.0.2.10")
connection = iec61850.IedConnection_create()
try:
    error = iec61850.IedConnection_connect(connection, host, 102)
    if error != iec61850.IED_ERROR_OK:
        raise RuntimeError(f"IEC 61850 connection failed: {error}")

    object_reference = "Bay01/LLN0.Mod.stVal"
    value, error = iec61850.IedConnection_readBooleanValue(
        connection, object_reference, iec61850.IEC61850_FC_ST
    )
    if error != iec61850.IED_ERROR_OK:
        raise RuntimeError(f"Read failed: {error}")
    print(f"{object_reference} = {value}")
finally:
    iec61850.IedConnection_close(connection)
```

The exact constructor and return shape can differ between binding releases, so run this against the installed package's bundled tests and pin the release that passes your integration tests. Many installations use `IedConnection_readObject` for general values or typed helpers such as `IedConnection_readFloatValue`, `IedConnection_readInt32Value`, and `IedConnection_readQualityValue`; choose the helper that matches the server's type and functional constraint. A protection relay may expose status under `ST`, measurements under `MX`, and commands under `CO`, but the server model is authoritative.

## Browse the model before hard-coding tags

A relay integration should discover or review the server model before reading values. Record the logical-device and logical-node names, data-object references, functional constraints, type information, quality, timestamps, and whether a value is reportable. Use SCL engineering files (`.icd`, `.scd`, or `.cid`) as the commissioning baseline, then compare that baseline with the live server during FAT/SAT. Do not infer that a familiar name such as `Mod.stVal` exists on every vendor's relay.

Keep the adapter's tag map explicit and reviewable. For example, map a protection status to a historian tag only after checking its quality and timestamp, and preserve the original IEC 61850 reference alongside the normalized tag. A stale or questionable status must not be converted into a healthy boolean merely because the Python value is `False`.

## Reports and control blocks

For event-driven SCADA integration, use report control blocks rather than polling every protection status at a fast interval. The binding includes operations such as `IedConnection_getRCBValues`, `IedConnection_setRCBValues`, `IedConnection_installReportHandler`, and `IedConnection_triggerGIReport`. Configure the report dataset, trigger options, integrity period, and reservation rules in accordance with the relay's SCL and vendor documentation. A general-interrogation report after reconnect helps resynchronize state, but it does not replace validation of sequence numbers, timestamps, and quality.

GOOSE and sampled values are time-critical Ethernet mechanisms, not ordinary request/response reads. `pyiec61850` exposes client control-block helpers for these services, but successful API calls do not prove that the host network, VLAN, multicast filtering, NIC, clock, or relay configuration is suitable. Validate those dependencies on an isolated test network before considering a GOOSE trip or sampled-value stream for operational use.

## Write commands carefully

Command writes are live-device operations. The binding offers typed methods such as `IedConnection_writeBooleanValue`, `IedConnection_writeInt32Value`, and `IedConnection_writeFloatValue`, as well as the general `IedConnection_writeObject`. A command-capable data object may require select-before-operate, an origin, an interlock, a time limit, or a vendor-specific control model; a successful transport call is not equivalent to an accepted or executed operation.

Use a dedicated command path that checks operator authorization, target identity, quality, freshness, and expected control model before writing. Log the original reference, requested value, response/error code, and subsequent indication. Test with a relay simulator or a non-energized test bay first; never use a copied example to issue a breaker operation.

## Safety notes

- **The first example is offline only.** Do not point it at a relay. The connection, report, GOOSE, sampled-value, and command examples require an approved IED or simulator and a controlled network.
- **IEC 61850 is protection and control infrastructure.** Treat MMS writes, GOOSE messages, and sampled values as safety-relevant. Use least privilege, an isolated commissioning VLAN, approved firewall rules, and change-controlled configuration.
- **Validate quality and time.** Check `Quality`, timestamps, test/invalid/blocked/substituted states, freshness, and server error codes before a value reaches alarms, interlocks, or automatic control.
- **Do not guess references or functional constraints.** Confirm them from SCL and the actual server model. Vendor naming, control models, report behavior, and supported services vary.
- **Plan for failure.** Handle disconnects, timeouts, reconnection, report loss, duplicate events, stale values, and clock issues. On uncertainty, fail safe and require an operator or protection engineer to decide the next action.
- **Check native compatibility.** `pyiec61850` depends on compiled libiec61850 bindings and may lack a wheel for a particular Python/platform combination. Pin and test the exact wheel or build used in the approved deployment.

Next door: use the [libiec61850 documentation and examples](https://libiec61850.com/), then validate the relay's SCL and control model with its vendor engineering tools before integrating `pyiec61850` into SCADA or protection workflows.
