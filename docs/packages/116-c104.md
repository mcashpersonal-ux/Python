# 98 — IEC 60870-5-104 with c104

> `c104` is a Python binding and simulator for IEC 60870-5-104, the TCP-based telecontrol protocol used between SCADA master stations and remote terminal units (RTUs) in substations and power-grid control systems. It models stations, information objects, measurements, commands, callbacks, and interrogation without requiring proprietary field hardware.

## Install

```bash
python -m pip install c104
```

`c104` 2.2.x provides prebuilt wheels for common manylinux x86_64/aarch64, Raspbian armv7l, and Windows x64 environments. The project currently documents Python 3.7 through 3.12; check the wheel list before using a newer interpreter. It wraps the native `lib60870-C` stack, so a source build may require a compiler and native build tools. The package is GPLv3-licensed.

## First example: offline point model

Start by testing the point and quality logic locally. This example uses only the Python standard library, so it is safe to run on a laptop or CI runner and does not open a port, contact an RTU, or issue a control command.

```python
from dataclasses import dataclass
from datetime import datetime, timezone

@dataclass
class GridPoint:
    common_address: int
    io_address: int
    type_id: str
    value: float
    quality: str = "GOOD"
    recorded_at: datetime | None = None

    def update(self, value: float, quality: str = "GOOD") -> None:
        self.value = value
        self.quality = quality
        self.recorded_at = datetime.now(timezone.utc)

voltage = GridPoint(47, 11, "M_ME_NC_1", 230.4)
voltage.update(231.1)
print(f"CA={voltage.common_address} IOA={voltage.io_address} "
      f"value={voltage.value:.1f} kV quality={voltage.quality}")
```

In IEC 104 terminology, the **common address (CA)** identifies a station and the **information object address (IOA)** identifies a measurement or command within it. The type identification (`M_ME_NC_1` above) determines how the value and cause of transmission are encoded on the wire. Keep this mapping documented alongside the substation's point list.

## Build a local RTU simulator

For an actual protocol test, run a server and client on the same machine. The server represents an RTU and exposes a measured value plus a command point; the client represents the SCADA master. This uses loopback only and is not a field-device connection. Put each snippet in its own file, start the server first, then start the client. Port 2404 is the conventional IEC 104 port; choose an unused high port when a local service already owns it.

**RTU/server (`rtu_demo.py`):**

```python
import random
import time
import c104


def before_read(point: c104.Point) -> None:
    point.value = 220.0 + random.random() * 20.0


def before_report(point: c104.Point) -> None:
    point.value = 220.0 + random.random() * 20.0


def on_switch_command(
    point: c104.Point,
    previous_info: c104.Information,
    message: c104.IncomingMessage,
) -> c104.ResponseState:
    print(f"received command IOA={point.io_address}, value={point.value}")
    return c104.ResponseState.SUCCESS


server = c104.Server(ip="127.0.0.1", port=2404)
station = server.add_station(common_address=47)
voltage = station.add_point(
    io_address=11, type=c104.Type.M_ME_NC_1, report_ms=2000
)
voltage.on_before_read(callable=before_read)
voltage.on_before_auto_transmit(callable=before_report)
switch = station.add_point(io_address=12, type=c104.Type.C_RC_TA_1)
switch.on_receive(callable=on_switch_command)

server.start()
print("RTU listening on 127.0.0.1:2404; press Ctrl-C to stop")
try:
    while True:
        time.sleep(1)
except KeyboardInterrupt:
    server.stop()
```

The periodic report callback runs only while a client is connected. A real RTU callback should validate command state, interlocks, select-before-operate policy, and operator authorization before changing equipment; returning `SUCCESS` here only acknowledges a demo command.

**SCADA/client (`scada_demo.py`):**

```python
import time
import c104

client = c104.Client()
connection = client.add_connection(
    ip="127.0.0.1", port=2404, init=c104.Init.INTERROGATION
)
station = connection.add_station(common_address=47)
voltage = station.add_point(io_address=11, type=c104.Type.M_ME_NC_1)
switch = station.add_point(io_address=12, type=c104.Type.C_RC_TA_1)
switch.value = c104.Step.HIGHER

client.start()
try:
    deadline = time.monotonic() + 10
    while connection.state != c104.ConnectionState.OPEN:
        if time.monotonic() >= deadline:
            raise TimeoutError("IEC 104 connection did not open")
        time.sleep(0.1)

    if voltage.read():
        print(f"interrogated voltage: {voltage.value}")
    if switch.transmit(cause=c104.Cot.ACTIVATION):
        print("switch command accepted by the client stack")
    time.sleep(2)
finally:
    client.stop()
```

`Init.INTERROGATION` asks the RTU for its current process image after connection. `Point.read()` requests one point, while `Point.transmit()` sends a client-side command. The exact command type, cause of transmission, and station address must match the RTU's engineered point list.

## Measurements, quality, and timestamps

Use the type that matches the information object defined by the substation gateway. For example, `M_ME_NC_1` is a normalized floating-point measurement; other `M_*` types represent single points, scaled values, counters, or timestamps. Set a point's value in the server callback and inspect `point.value`, `point.quality`, and `point.info` on the client after an interrogation or spontaneous report. Treat a questionable, blocked, substituted, or overflow quality flag as a data-quality event rather than silently storing it as a valid measurement.

```python
import c104

client = c104.Client()
connection = client.add_connection(
    ip="127.0.0.1", port=2404, init=c104.Init.INTERROGATION
)
station = connection.add_station(common_address=47)
point = station.add_point(io_address=11, type=c104.Type.M_ME_NC_1)
client.start()
try:
    if point.read():
        print("value:", point.value)
        print("quality:", point.quality)
        print("information:", point.info)
finally:
    client.stop()
```

This client snippet assumes the loopback RTU demo is already running. In production, replace the loopback address with an approved substation gateway and add connection supervision, bounded retries, and time-series logging.

## Commands and callbacks

A command point's `on_receive` callback is the control boundary. Use the callback to enforce an allow-list of values, check the current equipment state, record the operator and cause, and return `c104.ResponseState.FAILURE` when the operation cannot be safely executed. For a real breaker or tap changer, do not equate protocol acceptance with physical completion: wait for the corresponding status indication and alarm feedback.

For larger test fixtures, add several points to one station and use `c104.Batch` with `server.transmit_batch(...)` to report a coherent set of values. Use `connection.interrogation()` after reconnecting or after a communications gap so the SCADA image is rebuilt from a known snapshot.

## Connection lifecycle and diagnostics

Keep the client or server object alive for the entire session. Check `connection.state` and `server.has_active_connections` rather than assuming that `start()` means a peer is reachable. Add `on_state_change`, `on_send_raw`, or `on_receive_raw` callbacks when diagnosing sequence counters, causes of transmission, or an unexpected peer message; avoid logging sensitive operational data indefinitely. A failed connection should trigger an alarm and a controlled retry, not an uncontrolled tight loop.

## Safety notes

- **Do not point a demo client at a live substation.** Use `127.0.0.1`, a dedicated lab VLAN, or a vendor-approved simulator until the entire point list and command behavior are reviewed.
- IEC 104 commonly uses TCP port 2404. Firewall it to the required peers, segment the control network, and use the package's TLS support or an approved secure tunnel where the gateway and security architecture support it.
- Treat all remote commands as safety-critical. Implement least privilege, select-before-operate where required, interlocks, range checks, audit logging, and an independent engineering review before enabling writes.
- Confirm common addresses, IOAs, type IDs, causes of transmission, time bases, and quality semantics with the RTU/gateway configuration. A syntactically valid command can still target the wrong field object.
- `c104` is a simulator/binding, not a complete SCADA security or historian solution. Test reconnects, stale data, duplicate reports, clock behavior, malformed peers, and loss of communications before deployment.
